Project Overview

Welcome to the Portfolio CMS documentation. This project is a scalable, production-grade Full Stack Portfolio Management Platform engineered with enterprise software standards.

The system is strictly decoupled: the frontend consumes data exclusively through REST APIs, and the backend handles complex business logic, database management, and security, ensuring complete separation of concerns.

Core Philosophy: Everything visible on the portfolio website is dynamically manageable from the Admin Dashboard. There are no hardcoded data values.

Key Features

Dynamic Content Management

Fully manageable sections including Projects, Services, Skills, Experience, Education, and Testimonials via the Admin Panel.

Secure Authentication

JWT-based authentication with refresh tokens, password hashing via BCrypt, and secure role-based authorization.

Media Library

Centralized media and file organizer for uploading, managing, and picking assets for different content sections.

Premium UI/UX

Designed with glassmorphism, smooth animations (GSAP, Lenis), and modern typography inspired by Linear and Vercel.

Architecture & Stack

The platform follows Clean Architecture and SOLID principles.

Backend Stack (.NET 8)

  • Framework: ASP.NET Core 8 Web API
  • Database: PostgreSQL (via Entity Framework Core Code-First)
  • Patterns: Repository Pattern, Service Layer, Dependency Injection
  • Utilities: AutoMapper for DTOs, FluentValidation for robust model validation

Frontend Stack (Vanilla HTML/CSS/JS)

  • Structure: Semantic HTML5, CSS3 with CSS Variables
  • Logic: Modular ES6 JavaScript (No heavyweight frameworks)
  • Libraries: FontAwesome, GSAP for animations

How to Add a New Functionality

To introduce a new feature (e.g., a "Blog" module), you must implement it vertically across the stack. Follow this standard enterprise workflow.

1. Database Entity

Create the data model in Backend/Entities/. All models must use UUIDs for primary keys and include audit fields.

public class BlogPost : BaseEntity 
{
    public string Title { get; set; }
    public string Content { get; set; }
}

2. DTOs & Validation

Create Data Transfer Objects in Backend/DTOs/ to separate database models from API contracts. Add a validator in Backend/Validators/.

3. Repository & Service

Implement the data access in Backend/Repositories/ and business logic in Backend/Services/. Register them in Dependency Injection (Program.cs).

4. Database Migration

Add a DbSet to the `ApplicationDbContext`, configure relationships, and run Entity Framework migrations.

dotnet ef migrations add AddBlogTable
dotnet ef database update

5. REST API Controller

Expose endpoints in Backend/Controllers/. Ensure you use standard HTTP methods and proper route attributes.

6. Frontend Component

In Frontend/admin/components/, create a JavaScript module (e.g., blog-manager.js) that calls your new API via utils/api.js and renders the table/forms in the UI.

Strict Rule: Never bypass the API. The frontend must never contain business logic, and the backend must never output HTML.

Database & Migrations

We use Code-First Migrations. Never modify the PostgreSQL database manually. Every schema change must be tracked via EF Core.

Common Commands

# Create a new migration after changing an Entity
dotnet ef migrations add <DescriptiveName>

# Apply pending migrations to the database
dotnet ef database update

# Revert the last migration (if not yet pushed)
dotnet ef migrations remove

Extending the Admin Panel

The Admin Dashboard is built dynamically. To add a new page (e.g., Plugins):

  1. Create a script in Frontend/admin/components/new-manager.js following the IIFE module pattern (like window.NewManager = (() => {...})();).
  2. Add a sidebar link in Frontend/admin/pages/dashboard.html with a unique data-panel="newfeature" attribute.
  3. Add a container <section class="panel" id="panel-newfeature"> in dashboard.html.
  4. In the loadPanel switch statement within the dashboard logic, initialize your manager when the user clicks the link.

Plugins Architecture

The platform supports a WordPress-style plugin marketplace. Plugins are stored centrally and installed dynamically to the frontend.

Plugin Repository

All available plugins are stored as separate folders inside docs/plugins/. Each folder contains the frontend components and a plugin.json metadata file defining the plugin's ID, Name, Description, Version, and Files list.

Backend Control (PluginsController.cs)

The PluginsController is responsible for safely moving files on the disk to simulate an installation process. It provides:

  • GET /api/plugins/available: Scans docs/plugins, parses plugin.json files, and cross-references with Frontend/admin/components/ to determine which plugins are currently installed vs available.
  • POST /api/plugins/install/{id}: Physically copies the declared files from the repository directory to the active frontend components directory.
  • DELETE /api/plugins/{id}: Physically erases the plugin files from the active frontend directory, completely uninstalling the code.

Frontend (plugins-manager.js)

The UI fetches the available plugins and renders a "Plugin Repository" view where admins can search for and install plugins. Installed plugins can be activated/deactivated (state stored in browser localStorage) or fully deleted.

Coding Standards & Guidelines

  • C# Conventions: Follow Microsoft .NET naming standards (PascalCase for classes/methods, camelCase for local variables).
  • File Modification: Never overwrite or delete files blindly. Always preserve backward compatibility.
  • API Responses: Use standardized JSON wrappers for all API responses ensuring frontend clients can parse errors consistently.
  • DRY & KISS: Avoid duplicating logic. Keep components isolated and simple.

Classes Report

Detailed report of the core classes used in this project's backend architecture.

  • BaseEntity: The foundational class for all database entities, providing common properties like Id (UUID), audit tracking (CreatedAt, CreatedBy, UpdatedAt, UpdatedBy), and soft-delete capabilities (IsDeleted, DeletedAt, DeletedBy).
  • Page: Inherits from BaseEntity. Represents a custom page in the CMS. Stores properties such as Title, Slug, HtmlContent, CssContent, and Status.
  • PluginDto: A Data Transfer Object used to map and transfer plugin metadata (Id, Name, Version, Description, Icon, IsInstalled) between the server and the frontend.
  • ApiResponse<T>: A generic wrapper class used to standardize all HTTP responses. It includes properties for success status, a descriptive message, and the generic data payload.
  • PortfolioDbContext: The Entity Framework Core database context class responsible for managing database connections and providing DbSets for all entities (like Pages, Projects, Skills, etc.).
  • PagesController: An ASP.NET Core API Controller that handles HTTP requests for custom pages, implementing standard CRUD operations and ensuring proper RESTful routing and authorization.
